# 詳細設計フェイズ

## 概要

このコマンドは、要件をもとに関連アーキテクチャを確認し、実装方針とファイル構成の提案を作成するためのものである。既存の実装パターンを参照しながら、アーキテクチャ原則に準拠した提案を行うことを目的とする。
このコマンドでは、 **ジュニアエンジニアが実装可能なレベルでの具体的な実装を文書化すること** を詳細設計と呼ぶ。

* 計画ファイルとは、 `.ai-agent/plan/*.md` に保存された「要件定義・詳細設計・実装手順」等が記載されたファイルである

* Coding-Commandsのステップ2である
  1. `/coding.requirement`
  2. `/coding.design`
  3. `/coding.execute`

## 入力値

* 入力された計画ファイル

## 出力

* ジュニアエンジニアが作業可能な粒度の計画ファイル
* 入力された計画ファイルの更新を行う
  * 更新時の出力フォーマットは [design.md](../extra/coding/design.md) に準ずる

## ガードレール条項

* 計画ファイルは **新規作成してはならず、必ず上書き保存する**
* 実装差分を省略せず、レビュー可能な詳細度を保つ

## 作業手順

### ステップ1. 詳細設計実施

レビューのみを依頼された場合、このステップを実施しなくて良い

* [ ] 宣誓を行う

    ```text
    宣誓
    
    私は詳細設計を行います。
    計画ファイルのみを更新し、プロダクションコードに差分を与えないことを誓います。
    必要なSKILLは積極的に活用し、良き計画の実現のために提案を行います。

    このコマンド実行以後、私は `詳細設計モード` に入ります。
    ハーネスが適用され、計画ファイルのみを更新します。
    ユーザーが明示的に指示するまで、詳細設計と実装は行いません。
    ```

* [ ] 既存の計画ファイルの内容を確認する
* `/engineer.software-design` SKILLをロードする
* SKILLやドキュメントから、 `ジュニアエンジニア` の技能定義と提案粒度を確定する
* 与えられた文脈、及び要件定義の内容を実現するための **ジュニアエンジニアが作業可能な、具体的な変更差分** を提案し、計画ファイルに反映する

### ステップ2. 実装計画のレビュー

* [ ] `/coding-assistant.software-design-reviewer` Sub Agentを並列実行し、複数視点での並列レビューを行う
  * 批判的視点での実行:
    * ジュニアエンジニアが実装可能な、具体的な差分が提案されているか
    * ユーザーが指定した要件を満たしているか
    * プロジェクト内のベストプラクティス、既存コードと大きな乖離が無いか
    * 各種関連ドキュメントの内容が反映されているか、充足をレビューする
    * 一般的なセキュリティ及びコーディングのアンチパターンに抵触しないか
  * 中立的視点での実行:
    * ジュニアエンジニアが実装可能な、具体的な差分が提案されているか
    * ユーザーが指定した要件を満たしているか
    * プロジェクト内のベストプラクティス、既存コードと大きな乖離が無いか
    * 各種関連ドキュメントの内容が反映されているか、充足をレビューする
    * 一般的なセキュリティ及びコーディングのアンチパターンに抵触しないか
* [ ] すべてのレビューが完了するのを待つ
* [ ] 指摘内容を下記フォーマットに整理して出力する

    ```markdown
    # 指摘内容

    ## 指摘1. {指摘内容のサマリ}

    {詳細}

    <!-- 
    `コメント不足` 等の非破壊的かつ悪影響のない変更は"必須"扱いで良い.
     -->

    変更の推奨度: {低/中/高/必須}
    推奨理由: {推奨理由}

    ## 指摘1. {指摘内容のサマリ}

    {詳細}

    変更の推奨度: {低/中/高/必須}
    推奨理由: {推奨理由}
    ```

### ステップ3. 詳細設計の改善

* [ ] 指摘内容をセルフレビューし、下記の基準に基づいて計画ファイルに反映する
  * 2人以上のレビュアーが指摘: 反映する
  * `具体性が足りない` という旨の指摘: 反映する
  * 内容を判断し、適切と考える指摘: 反映する
  * その他は保留として扱う
* [ ] レビュー結果を元に、ユーザーに次のアクションを伝える

    ```markdown
    私は `詳細設計モード` です。
    宣誓に従い、ユーザーが明示的に指示するまで、実装は行いません。
    計画ファイルは [{ファイル名}](path/to/markdown.md) です。
    続きの指示は、全て詳細設計についての指示として解釈します。


    例: `計画の修正指示...`
    例: `/coding.design 実装修正を行い、再レビュー`
    例: `/coding.execute すべてのステップを実行してください`
    例: `/coding.execute ステップXまで完了させてください`
    ```
