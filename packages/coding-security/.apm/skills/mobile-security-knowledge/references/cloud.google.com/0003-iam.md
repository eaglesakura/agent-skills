# Google Cloud IAM を安全に使う

## 概要

本ドキュメントは [Use IAM securely](https://cloud.google.com/iam/docs/using-iam-securely) と [Best practices for service accounts](https://cloud.google.com/iam/docs/best-practices-service-accounts) を蒸留したものである。最小権限、人間とサービスアカウントの分離、鍵ファイル回避を監査観点へ落とす。

* 正本: <https://cloud.google.com/iam/docs/using-iam-securely>
* SA: <https://cloud.google.com/iam/docs/best-practices-service-accounts>
* Firebase IAM: [`../firebase.google.com/0004-iam.md`](../firebase.google.com/0004-iam.md)

## 最小権限とグループベース付与を使う

個人への広い基本ロール（Owner / Editor）を避け、職務グループへ事前定義ロールまたはカスタムロールを付与する。

### 最小権限とグループベース付与を使うの補足

* 利点: 権限棚卸しと退職時の回収が容易になる
* 注意点: Firebase Console に見えるメンバーは基本／Firebase 事前定義ロール中心。SA は Cloud Console IAM で確認する
* 適用範囲: 人間ユーザー、グループ、CI
* 例外: 初期ブートストラップの一時 Owner（期限と交代手順を残す）

### 最小権限とグループベース付与を使うの実装例

```text
チェック
* 本番は Viewer / 限定 Admin を原則
* setIamPolicy 相当は少数の Owner のみ
* IAM Recommender で過剰権限を定期確認
* Deny policies が使える場合は破壊的操作を拒否
```

## サービスアカウントは鍵ファイルよりフェデレーション／ADC

長期のサービスアカウント鍵 JSON を新規発行しない。Cloud Run / GKE / CI では Workload Identity または Application Default Credentials を使う。

### サービスアカウントは鍵ファイルよりフェデレーション／ADC の補足

* 利点: 鍵の紛失・リポジトリ混入リスクを減らせる
* 注意点: ローカル開発は `gcloud auth application-default login` を優先
* 適用範囲: Cloud Run、Functions、GKE、GitHub Actions 等
* 例外: どうしても外部が鍵必須の場合は Secret Manager 保管・短命・ローテーション必須

### サービスアカウントは鍵ファイルよりフェデレーション／ADC の実装例

```text
推奨
* Cloud Run: ランタイム SA + 最小ロール
* CI: Workload Identity Federation
* 禁止: リポジトリ内の *-sa.json / .env への秘密鍵コミット
```

## ナレッジベース

### DO: 人間とワークロードの権限を別プリンシパルで設計する

```text
# 推奨
humans: groups + predefined roles
workloads: dedicated SA + WIF/ADC
review: quarterly IAM recommender
```

### DO NOT: 共有 Editor とダウンロード済み SA 鍵で「とりあえず動かす」

* 理由: 公式が鍵ファイルよりフェデレーションを推奨している
* 理由: 漏洩時の影響がプロジェクト全体に及ぶ

```text
# DO NOT: 1 つの SA 鍵を全員で共有

# DO: ワークロード別 SA + 鍵レス認証
```
